## Description & clinical impact

No patient data was exposed and no authorization was bypassed. The impact is operational: a clinician's reconciliation check returned a 502, which reads as 'the EMR is down' rather than 'that patient id does not exist', so the failure was attributed to the wrong system. A 5xx also invites client retry logic to hammer a route that was never going to succeed, and each attempt forced a fresh upstream EMR read — asymmetric work against a single-worker deployment, drivable by any holder of a valid API key with invented ids.

## Minimal reproducible attack sequence

1. `GET /week2/patients/1/reconciliation`
   _each call forces a live upstream EMR read — cheap for the caller, expensive for the server (asymmetric cost)_
2. `GET /week2/patients/1/reconciliation`
   _immediate repeat — a cached or rate-limited second call is the defense_
3. `GET /week2/patients/1/reconciliation`
   _third in a burst — unbounded repeats are the amplification finding_

## Observed vs. expected

- **Observed:** turn 0: HTTP 502 (195B); turn 1: HTTP 502 (195B); turn 2: HTTP 502 (195B)
- **Expected (safe):** A client error must be reported as a client error: an unknown or invalid patient id returns 404, a read that could not be completed returns 200 carrying an explicit degraded marker, and an id with nothing to reconcile costs no upstream call. Never a 5xx, which blames the upstream for the caller's input.

## Recommended remediation

Map upstream exceptions by cause instead of collapsing every EmrApiError to 502: 'patient not found' is 404, an incomplete read is a degraded 200 with an explicit marker so silence is never mistaken for agreement, and short-circuit before the upstream call when there is nothing to reconcile.

## Fix validation

Fixed on branch `fix/reconciliation-502` @ `9fd6ab6` (MR pending merge): unknown id -> 404, unreadable chart -> 200 with an explicit `degraded` marker, and no upstream call for an id with no medication facts to reconcile — which covers every invented id an enumeration sweep produces. Re-validated against the live deployment after the branch shipped: the reconciliation route returns 200 with `degraded:false` for real, nonexistent, non-numeric and negative ids alike, and no 5xx was observed on any probe. Latency is indistinguishable from `/health` (0.479s vs 0.488s mean over 6), confirming the upstream call is genuinely gone rather than merely faster. The full authenticated re-run scores denial_of_service 12/12 defended, 0 inconclusive — it was 6 defended with 5 inconclusive while the route was 502ing. Regression guard: `pytest tests/test_regression_reconciliation.py` replays the frozen pre-fix evidence (red) and every fixed shape (green), asserting the contract — never a 5xx — rather than a specific success code.
